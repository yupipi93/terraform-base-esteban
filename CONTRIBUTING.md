# Contributing

This repository is a Terraform template for Google Cloud, driven
by YAML settings, with three reference workspaces (dev, stg and pro). Read
`README.md`, `docs/PROJECT_STRUCTURE.md` and `AGENTS.md` before a first change;
`AGENTS.md` holds the conventions every change follows, for people and agents alike.

## Setup

| Tool | Version | Why |
|---|---|---|
| Terraform | `>= 1.14.0` (`required_version` in `versions.tf`; CI uses 1.14.5) | fmt, validate, test |
| tflint | the version in `.github/workflows/terraform.yml` (v0.66.0), with the google ruleset of `.tflint.hcl` | lint of the root module |
| pre-commit | any recent release | runs the hooks of `.pre-commit-config.yaml` before each commit |
| Python | 3.12 or later, with PyYAML and jsonschema | the scripts under `bin/` |

```bash
tflint --init                      # downloads the ruleset pinned in .tflint.hcl
pip install pre-commit && pre-commit install

# Python dependencies, either way:
uv run --no-project --with pyyaml --with jsonschema python3 bin/validate-settings.py
python3 -m pip install pyyaml jsonschema
```

No GCP login is needed for any check below. None of them plans against a real
project.

## Checks to run before a pull request

CI (`.github/workflows/terraform.yml`) runs most of these on every pull request.
Run them locally first:

```bash
# Format the root files and the tests
find . \( -name '*.tf' -o -name '*.tftest.hcl' \) -not -path './modules/*' -not -path './.terraform/*' -print0 \
  | xargs -0 terraform fmt -check -diff

# Lint the root module
tflint --format compact --minimum-failure-severity=warning

# Validate the default workspace
terraform init -backend=false -input=false
terraform validate

# Validate dev, stg, pre and pro with a local backend override (gitignored)
printf 'terraform {\n  backend "local" {}\n}\n' > backend_override.tf
terraform init -reconfigure -input=false
for ws in dev stg pre pro; do
  terraform workspace select "$ws" 2>/dev/null || terraform workspace new "$ws"
  terraform validate
done
terraform workspace select default
rm backend_override.tf
terraform init -reconfigure -backend=false -input=false

# Plan the reference shapes with mock providers
terraform test

# Settings files against schemas/settings.schema.json
python3 bin/validate-settings.py

# The Cloud Build renderer agrees with the pipeline
python3 bin/cloudbuild-render-test.py

# No open p0 item, and no leaked name or address
python3 bin/audit-terraform.py --fail-on p0
python3 bin/audit-terraform.py --leaks
```

`--leaks` scans every tracked file for real-looking emails. A fork cut from a
private stack lists that stack's names, one regular expression per line, in a
gitignored `.audit-denylist`, or in a file named by `AUDIT_DENYLIST`:

```bash
AUDIT_DENYLIST=/path/to/private-denylist.txt python3 bin/audit-terraform.py --leaks
```

Any `leak` line must be fixed before the pull request. A change that adds a
settings key also adds it to `schemas/settings.schema.json` and documents it in
`settings/example.yaml` and the matching page under `docs/`.

## One backlog item per pull request

The work list is `docs/audit/BACKLOG.md`, generated by `bin/audit-terraform.py`
from checks on the code. `docs/audit/OPERATING.md` describes the loop. In short:

1. Take one item (`python3 bin/audit-terraform.py --next`) and change only what
   it needs. A drive-by fix belongs in its own item.
2. Branch as `<type>/<id-lower>-<short-slug>`, for example
   `fix/aud-sql-pitr-wire-backup`.
3. `python3 bin/audit-terraform.py --id <ID>` must exit 0. Then run
   `python3 bin/audit-terraform.py --write` and commit the refreshed backlog in the
   same pull request.
4. Fill in the pull request template: summary, changes, validation, rollback and
   the item id.

A change outside the backlog (a typo, a new idea) is welcome too: open an issue
first when it changes behaviour, so it can become an item with a check.

## Commits

[Conventional Commits](https://www.conventionalcommits.org/):
`<type>(<scope>): <description>`, with `feat`, `fix`, `docs`, `style`,
`refactor`, `test`, `chore`, `build`, `ci` or `perf`. Put the item id at the end
of the subject, for example
`fix(sql): wire point-in-time recovery into the module (AUD-SQL-PITR)`. Stage
explicit paths, and never commit `backend.hcl`, state, plans, `.env` files or
secret values.

## Never apply from a pull request

A pull request is reviewed as code. Nobody runs `terraform apply` or
`terraform destroy` from a pull request, a fork or CI, and a pull request is
not an approval to apply. An apply is a separate decision by whoever owns the
target project, on a plan they have read, in that workspace. The reference
settings carry placeholders (`example-app-<env>`, `replace-me@example.com`) and
are not meant to be applied as they are.

## Security issues

Do not open a public issue for a vulnerability. See [SECURITY.md](SECURITY.md).
